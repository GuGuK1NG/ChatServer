# Qt 重构聊天室客户端 —— 实现思路

服务端在 `D:\CR`（muduo + MySQL + Redis + nlohmann/json），客户端要从 Linux 终端版
`D:\CR\src\client\main.cpp`（545 行）重构成 Qt 图形界面，项目在 `D:\QtFlie\QtChatRoomClient`
（Qt 6.11.1 MinGW，CMake）。

**本轮范围**：登录 + 注册 + 好友列表 + 一对一私聊。群组、加好友后续迭代。

**风格约定**：CMake 构建；`.ui` + `ui->xxx`；Qt5 函数指针语法连接信号槽（不用 lambda）；
槽名走 Designer 自动连接的 `on_<objectName>_<signal>`；自定义类用 `Q` 前缀；成员变量 `m_` 前缀，
`ui` 指针固定叫 `ui`；代码/API 英文，注释与 UI 文案中文。

## 一、整体框架

三层，界面层和网络层通过信号槽解耦，谁也不 include 谁的具体实现：

```
┌─────────────────────────────────────────────┐
│  main.cpp                                    │
│    登录对话框 exec() 门控 → 通过后才起主窗口    │
├─────────────────────────────────────────────┤
│  界面层                                       │
│   LoginDialog   RegisterDialog   MainWindow  │
│        └──── 只发信号 / 收信号 ────┘          │
├─────────────────────────────────────────────┤
│  通信层  QChatClient : QTcpSocket (单例)      │
│    发包 packMsg() │ 收包 consumeBuffer()      │
├─────────────────────────────────────────────┤
│  数据层  protocol.h(常量)  user.h(结构体)     │
└─────────────────────────────────────────────┘
              ↓ TCP 裸 JSON
        服务端 D:\CR 的 ChatServer
```

**核心决策：网络层做成单例 + 继承 QTcpSocket。**

理由：TCP 连接的生命周期比任何一个窗口都长。登录对话框 `exec()` 返回后会被析构，但连接必须
活着给主窗口用。做成单例就绕开了「跨窗口传 socket 指针」这件事 —— `MainWindow` 任何时候
`QChatClient::instance()` 拿到的都是同一条活连接。

单例的静态对象**不要给 parent**（传 `nullptr`）。给 `qApp` 会在 `QApplication` 析构时被
delete，而静态对象析构是另一套时机，容易二次释放。

## 二、必须先吃透的服务端约束

这是整个重构最容易翻车的地方。

服务端 `D:\CR\src\server\chatserver.cpp`：

```cpp
string buf = buffer->retrieveAllAsString();
json js = json::parse(buf);     // 裸解析
```

全仓库**没有** `LengthHeaderCodec`、没有长度前缀、没有换行分隔符。这推出两条硬性要求：

### 1. 发送：一次 write 只发一条完整 JSON，尾部补 `'\0'`

终端客户端的既有约定（`D:\CR\src\client\main.cpp` 里 8 处）都是：

```cpp
send(fd, request.c_str(), strlen(request.c_str()) + 1, 0);   // 注意 +1, 带上 '\0'
```

Qt 侧照搬。`QByteArray` 可以内含 `'\0'` 并原样 `write()`，但
`QJsonDocument::toJson(Compact)` 不会产生 `'\0'`，得手动补：

```cpp
inline QByteArray packMsg(const QJsonObject &js)
{
    QByteArray data = QJsonDocument(js).toJson(QJsonDocument::Compact);
    data.append('\0');
    return data;
}
```

把这个约定收敛到**唯一一个函数**里 —— 万一实测服务端解析不了，只改这一处。

### 2. 接收：必须自己写增量拆包器

服务端所有回包（`chatservice.cpp:79,139,148,169,178,248,324,367`）都是裸 JSON，
**没有终止符**。如果一次 `readyRead` 收到两条黏在一起的消息，`QJsonDocument::fromJson`
只解析第一条、把其余的丢掉。

### 协议速查

```
LOGIN_MSG=1  REG_MSG=2  REG_MSG_ACK=3  LOGIN_MSG_ACK=4  PRIVATE_CHAT_MSG=5
ADD_FRIEND_MSG=6  CREATE_GROUP_MSG=7  ADD_GROUP_MSG=8  GROUP_CHAT_MSG=9  LOGOUT_MSG=10
```

**登录响应**（`errno`: 0 成功 / 1 用户名或密码错 / 2 该账户已登录）：

```json
{"msgid":4,"errno":0,"id":1,"name":"GGK",
 "offlinemsg":["{...}","{...}"],
 "friends":["{\"id\":2,\"name\":\"GK\",\"state\":\"online\"}"]}
```

两个坑：**失败时没有 `id`/`name` 字段，只有 `errmsg`**；`friends` 和 `offlinemsg` 是
**字符串数组**，每一项还得再 `fromJson` 一次（终端版里那句 `json::parse(str)` 就是这个动作）。

**注册响应**：`{"msgid":3,"errno":0,"name":"GGK","id":5}`，`errno!=0` 表示用户名已存在。

**私聊广播**：`{"msgid":5,"id":1,"name":"GGK","toid":2,"msg":"你好","time":"..."}`
—— 服务端原样回吐，客户端收到直接渲染即可。

### 4.3 `qchatclient` —— 通信核心

继承 `QTcpSocket` 而不是持有指针，让类本身就是会话对象：

```cpp
class QChatClient : public QTcpSocket
{
    Q_OBJECT
public:
    static QChatClient *instance();
    void connectToServer(const QString &host, quint16 port);
    bool isReady() const;

    void sendLogin(const QString &name, const QString &pwd);
    void sendRegister(const QString &name, const QString &pwd);
    void sendPrivateChat(int toid, const QString &msg);
    void sendLogout();

    int myId() const;  QString myName() const;
    QList<User> friends() const;  User friendById(int id) const;

signals:
    void loginResult(int errno, const QString &errmsg);
    void regResult(int errno, const QString &name, int id);
    void privateChatReceived(const ChatMessage &msg);
    void linkStateChanged(bool connected, const QString &text);

private slots:
    void onReadyRead();
    void onSocketStateChanged(QAbstractSocket::SocketState s);

private:
    explicit QChatClient(QObject *parent = nullptr);
    Q_DISABLE_COPY(QChatClient)
    void dispatch(const QJsonObject &js);
    void consumeBuffer();                       // ← 核心算法, 见第五节
    QByteArray m_buf;                           // 接收累积缓冲
    int m_myId = -1;  QString m_myName;
    QList<User> m_friends;
};
```

构造函数里接两个信号：

```cpp
connect(this, &QAbstractSocket::readyRead,    this, &QChatClient::onReadyRead);
connect(this, &QAbstractSocket::stateChanged, this, &QChatClient::onSocketStateChanged);
```

`connectToServer()` 要注意**重连前先 `abort()`**，否则 `connectToHost` 在已有连接上调用
行为不确定：

```cpp
void QChatClient::connectToServer(const QString &host, quint16 port)
{
    m_buf.clear();
    if (state() == QAbstractSocket::ConnectedState && peerAddress().toString() == host
        && peerPort() == port) return;          // 已经连着同一地址, 不重复连
    abort();
    connectToHost(host, port);
}
```

`dispatch()` 就是按 `msgid` 分发的 switch：`LOGIN_MSG_ACK → handleLoginAck`、
`REG_MSG_ACK → handleRegAck`、`PRIVATE_CHAT_MSG → handlePrivateChat`，其余 `qDebug()` 忽略。

`handleLoginAck` 里除了存 `m_myId/m_myName/m_friends`，还要**先把 `offlinemsg` 逐条
emit `privateChatReceived`、再 emit `loginResult`** —— 顺序反了主界面就收不到离线消息
（见 4.6 关键点 1）。

`onSocketStateChanged` 把 `ConnectedState`/`UnconnectedState` 翻译成
`linkStateChanged(bool, QString)`，界面据此把状态文字染绿/染红（沿用现有的
`setStyleSheet("color: green")` 写法）。

**关键点 1：好友列表要主动拉，不要靠信号。**

`loginResult` 信号在 `accept()` 时就发完了，而 `MainWindow` 那时还没构造，
**信号是同步的，错过就永久错过**。所以构造函数里直接读：

```cpp

for (const User &u : c->friends()) {
    auto *item = new QListWidgetItem(ui->listWidgetFriends);
    item->setData(Qt::UserRole, u.id);
    item->setText((u.isOnline() ? "● " : "○ ") + u.name);
}
ui->labelUser->setText(QString("%1(%2)").arg(c->myName()).arg(c->myId()));
```

**关键点 2：会话记录按好友 id 分开存。**

```cpp
QHash<int, QString> m_history;    // 好友id → 已渲染的 HTML
int m_currentFriendId = -1;       // 当前正在看的会话
```

- 点好友（`on_listWidgetFriends_itemClicked`）→ `m_currentFriendId` 更新，
  `textChat->setHtml(m_history[id])`
- 收到消息（`onPrivateChatReceived`）→ 判断这条是谁发的：
  - `msg.id == myId()` → 会话对象是 `msg.toid`，渲染成「我」
  - 否则 → 会话对象是 `msg.id`，渲染成 `msg.name`
  - 追加进 `m_history[那个id]`；如果正好等于 `m_currentFriendId` 就同步刷新视图，
    否则给那个好友项加未读标记

**关键点 3：渲染必须转义。**

```cpp
QString line = QString("<span style='color:#888'>%1</span> <b>%2</b>: %3<br>")
                   .arg(msg.time, who, msg.msg.toHtmlEscaped());   // ← 少了它就完蛋
```

`QTextBrowser` 认 HTML，对方发一句 `<b>你好` 就能把整个消息区搞乱。
`.toHtmlEscaped()` 是必须的。

**关键点 4：发送槽要挡未选会话。**

```cpp
void MainWindow::on_btnSend_clicked()
{
    auto *item = ui->listWidgetFriends->currentItem();
    if (!item) { QMessageBox::warning(this, "提示", "请先选择好友"); return; }
    const QString text = ui->lineEditMsg->text().trimmed();
    if (text.isEmpty()) return;
    QChatClient::instance()->sendPrivateChat(item->data(Qt::UserRole).toInt(), text);
    ui->lineEditMsg->clear();

```

`btnSend` 的 clicked 和 `lineEditMsg` 的 returnPressed 连**同一个**槽。

**关键点 5：关窗要发注销。**

`closeEvent()` 里发 `LOGOUT_MSG`。因为服务端靠 `clientCloseException` 或 `LOGOUT_MSG`
把用户状态改回 offline，客户端被强杀时服务端可能来不及清理，**下次登录就会被判
「该账户已经登录」（errno=2）**。正常关窗能避免这个。

### 4.7 `main.cpp` —— 登录门控

沿用 test11 的骨架，那是唯一的「登录 → 主界面」流程范例：

```cpp
int main(int argc, char *argv[])
{
    QApplication a(argc, argv);
    LoginDialog dlg;
    if (dlg.exec() == QDialog::Accepted) {
        MainWindow w;
        w.show();
        return QApplication::exec();
    }
    return 0;
}
```

这里有个新手容易担心的点：登录是**异步**的（发完 JSON 要等 `readyRead`），而 `exec()`
是阻塞的 —— 能行吗？

**能行。** `exec()` 开的是**嵌套事件循环**，照样派发 socket 的 `readyRead`，槽函数照常
执行，槽里调 `accept()` 就能让 `exec()` 返回。跟模态对话框里能弹文件对话框、能跑定时器
是一个道理。

## 五、最关键的两个算法

### 5.1 拆包器 `consumeBuffer()`（重点中的重点）

单纯用 `fromJson` 试解析是不行的，因为**多条黏包时它只返回第一条、把后面的丢掉**。
必须按大括号配对自己切。

但要小心：**消息正文里可能出现 `{` `}` `"` `\`**。用户发一句 `{"a":1}` 或者
`he said "hi"`，如果无脑数字符，就会在第 3 个字符处误判消息结束。所以必须区分
「字符串内的括号」和「结构括号」：

```
扫描 m_buf, 维护 depth(嵌套深度) / start(本条起点) / inString / escaped

对每个字符 c:
  if (inString):
        if (escaped)      escaped = false
        else if (c=='\\') escaped = true          // 反斜杠转义, 下一个字符不做判定
        else if (c=='"')  inString = false
        continue                                   // 字符串里的一切括号都不算数

  if (c == '"')      inString = true               // 进入字符串
  else if (c == '{') { if (depth==0) start = i;  ++depth }
  else if (c == '}') {
        if (depth > 0) {
            --depth
            if (depth == 0) {                      // 配平了, 切出一条完整消息
                chunk = m_buf.mid(start, i-start+1)
                fromJson(chunk) → 成功则 dispatch, 失败则 qWarning 丢弃(不能卡死缓冲)
            }
        } else {                                   // 落单的 '}', 前面是脏数据
            m_buf.remove(0, i+1);  i = -1           // 丢掉它及之前的内容, 重扫
        }
  }

扫描结束后:
    if (depth == 0) m_buf.clear()                  // 没有未完成的消息
    else            m_buf.remove(0, start)         // 保留不完整的尾巴, 等下次 readyRead 续上
```

`escaped` 那个标志位是必须的 —— 否则正文里的 `\"` 会被当成字符串结束符，后面全乱。
最后一步「保留尾巴」也是必须的 —— 一条消息被 TCP 切成两次 `readyRead` 是常态，
不能当成解析失败丢掉。

`onReadyRead()` 就两行：

```cpp
void QChatClient::onReadyRead() { m_buf.append(readAll()); consumeBuffer(); }
```

## 六、坑清单

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | 拆包器不处理字符串内的括号 | 对方发 `{"a":1}` 就丢消息/错乱 | 5.1 的 `inString`/`escaped` |
| 2 | 一次 write 分多条 / 忘了补 `'\0'` | 服务端 `json::parse` 抛异常，连接断 | 统一走 `packMsg()` |
| 3 | 靠信号给 MainWindow 传好友列表 | **永远收不到**（信号早发完了） | 构造时主动 `friends()` |
| 4 | 离线消息在 `loginResult` 之后才发 | 主界面漏掉离线消息 | `handleLoginAck` 里调整 emit 顺序 |
| 5 | `msg.msg` 不转义就塞进 HTML | 对方能搞乱你的消息区 | `.toHtmlEscaped()` |
| 6 | 失败响应里读 `js["id"]` | 拿到默认值 0，不是崩溃但脏 | 只在 `errno==0` 时读 id/name |
| 7 | 单例给了 `qApp` 当 parent | 析构时机冲突，可能二次释放 | parent 传 `nullptr` |
| 8 | 重连前不 `abort()` | `connectToHost` 行为不确定 | `connectToServer` 里先 abort |
| 9 | 关窗不发 `LOGOUT_MSG` | 服务端状态残留 `online`，下次登录被拒 errno=2 | `closeEvent()` 里发 |
| 10 | 中文乱码 | 见下 | 见下 |

**关于中文乱码**：服务端 `D:\CR\src\server\db\mysql.cpp` 附近用了
`mysql_query(_conn, "set names gbk")`，MySQL 连接字符集是 GBK，而 JSON 走 UTF-8。
终端客户端在 Linux 上没暴露这个问题，Qt 发 UTF-8 中文**有可能**乱码。

**先按 UTF-8 发，别提前优化。** 实测真乱码了，再在 `packMsg()` 里对 `msg` 字段做
UTF-8→GBK 转换（`QString::toLocal8Bit`）。因为收敛在单一入口，改动就一处。

## 七、建议的实现顺序

一步一个验证点，别一次写完再调：

1. **先跑通服务端** —— `ChatServer` 是 Linux ELF（`D:\CR\bin\ChatServer`），
   Windows 跑不了，要在 WSL/Linux 里 `./ChatServer 0.0.0.0 6000`，MySQL + Redis 先就绪
   （`D:\CR\include\server\db\mysql.h:9-12`：127.0.0.1 / root / 12345678 / 库名 `chat`）。
2. **用终端 `./ChatClient <ip> 6000` 确认服务端没问题** —— 先排除服务端变量，
   别把自己的坑赖到服务端头上。
3. `protocol.h` + `user.h`（半小时的事）
4. `qchatclient` 先只做**登录**：`onReadyRead` 里暂时直接 `fromJson` 不做拆包，
   能登录成功了再上拆包器。**分步走**，这样如果登录不通，能立刻知道是协议问题还是
   拆包问题。
5. `logindialog` + `main.cpp` 门控 —— 跑到能弹出主窗口就停。
6. `mainwindow` 填好友列表。
7. **最后补 `consumeBuffer()` 拆包器**，然后专门压测：开两个客户端互发，
   **连续快速发十几条**，看有没有丢。这一步是拆包器的验收测试。
8. 压测离线消息：对方离线时发几条，对方再登录，**每条都要完整显示**。

第 7、8 步是这个方案唯一没有现成方案可抄的地方，值得多花点时间。
