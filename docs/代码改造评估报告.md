## 一、总体结论

这是一个**功能完整、分层清晰**的 C++ 聊天室项目（muduo 网络库 + MySQL + Redis，C/S 架构）。架构设计合理 —— 网络层 / 业务层 / 数据层三层分明，消息路由用 `msgid → handler` 表驱动，Redis 双连接设计（publish / subscribe 分离）是正确的工程判断。

**但它把重心放在了"功能跑通"，而非"网络编程的正确性"。** 具体表现为：

| 维度 | 评价 |
|---|---|
| 架构分层 | ✅ 良好 |
| 功能覆盖 | ✅ 注册/登录/私聊/好友/群组/离线消息齐全 |
| **网络正确性** | ❌ **致命缺陷**：无分帧，粘包/拆包必崩 |
| **并发安全** | ❌ 读写锁误用，存在数据竞争 |
| 安全性 | ⚠️ SQL 注入、密码明文 |
| 健壮性 | ⚠️ 无心跳、无超时、断线处理粗暴 |
| 可维护性 | ⚠️ 无测试、无连接池、配置硬编码 |
| 资源管理 | ⚠️ 每操作新建连接；一处指针释放错误 |

**最该优先处理的是 P0-1（分帧）** —— 它是唯一一个**在正常使用中就会触发**、且后果为"消息静默丢失"或"服务端抛异常"的缺陷。其余 P0 项属于特定时序/特定数据下才触发。

## 二、P0 级问题（导致错误行为或崩溃）

### P0-1 消息无分帧，TCP 粘包/拆包必崩 🔬

**位置**
- 服务端：`src/server/chatserver.cpp:38-40`
- 客户端：`src/client/main.cpp:289-296`

**当前实现**

服务端 `onMessage` 拿到的是一条 TCP 流，但代码把它**整体当作一条消息**：

```cpp
// src/server/chatserver.cpp:38-40
string buf = buffer->retrieveAllAsString();   // 取走缓冲区里"全部"字节
json js = json::parse(buf);                   // 当作一条完整 JSON 解析
```

客户端接收侧同样问题：

```cpp
// src/client/main.cpp:289-296
char buffer[1024] = {0};
int len = recv(clientfd, buffer, 1024, 0);
if (-1 == len || 0 == len) { close(clientfd); exit(-1); }
json js = json::parse(buffer);                // 同上，无边界判断
```

**协议约定**：客户端发送时在末尾加 `\0`（见 `src/client/main.cpp:140,174,419,434,459,474,500,514` 均为 `strlen(...) + 1`），服务端按此约定解析。**但这个约定只在"一次 send 恰好对应一次 onMessage"时成立。**

**🔬 实测结果**

我在运行中的服务端上构造了两种真实网络情况：

| 测试 | 构造方式 | 实测结果 |
|---|---|---|
| **粘包** | 一次 `send()` 写入两条完整消息（共 106 字节） | 服务端**仅处理第一条**，第二条**静默丢弃**，无任何报错 |
| **拆包** | 一条 53 字节消息分两次 `send()`（间隔 1.5 秒） | 服务端抛异常：<br>`[json.exception.parse_error.101] parse error at line 1, column 27: syntax error while parsing value - invalid string: missing closing quote; last read: '"spli'` |

**为什么这是 P0**

TCP 是**字节流**协议，不保留消息边界。以下场景都会触发：

- 聊天消息较长，超过单次 TCP 段
- 用户快速连发两条消息
- 网络拥塞导致分段
- 客户端与服务端处理速度不匹配

**后果**：消息静默丢失（粘包）或业务处理异常（拆包）。这是**正常使用中就会遇到**的问题，不是极端边界情况。

**修改建议**

服务端 —— 利用 muduo `Buffer` 的查找能力，按 `\0` 切分并循环消费：

```cpp
// 思路示意，非成品代码
void ChatServer::onMessage(const TcpConnectionPtr &conn, Buffer *buffer, Timestamp time)
{
    while (true)
    {
        const char *eol = buffer->findCRLF();  // 或自行查找 '\0'
        // 累积接收缓冲区，直到找到分隔符才解析一条完整消息
        // 解析后继续循环，处理剩余字节
    }
}
```

客户端 —— 维护接收缓冲区，累积到 `\0` 才解析：

```cpp
// 思路示意
static std::string recvBuf;                 // 跨 recv 累积
char tmp[1024];
int n = recv(clientfd, tmp, sizeof(tmp), 0);
recvBuf.append(tmp, n);
size_t pos;
while ((pos = recvBuf.find('\0')) != std::string::npos)
{
    std::string oneMsg = recvBuf.substr(0, pos);
    recvBuf.erase(0, pos + 1);
    json js = json::parse(oneMsg);
    // 处理这一条
}
```

**验证方式（改完可立即回归）**：重跑本文附录中的粘包与拆包两个用例，应分别收到 **2 条**响应与 **1 条**正常响应。

### P0-2 登录/注销误用读锁修改共享容器 👁

**位置**：`src/server/chatservice.cpp` 五处

| 行号 | 操作 | 锁类型 | 问题 |
|---|---|---|---|
| `86` | `_userConnMap.insert({id, conn})`<br>`_connUserMap.insert({conn, id})`（`:87-88`） | `std::shared_lock` | ⚠️ **写操作持读锁** |
| `210` | `_userConnMap.erase` / `_connUserMap.erase`（`:215-216`） | `std::shared_lock` | ⚠️ **写操作持读锁** |
| `345` | `_userConnMap.erase` / `_connUserMap.erase`（`:346-347`） | `shared_lock` | ⚠️ **写操作持读锁** |
| `237` | 仅 `find`（`:238`） | `shared_lock` | ✅ 正确 |
| `303` | 仅 `find`（`:309`） | `shared_lock` | ✅ 正确 |
| `358` | 仅 `find`（`:359`） | `shared_lock` | ✅ 正确 |

**问题分析**

`std::shared_mutex` 的设计是：**读者可并发进入，写者独占**。代码在 `login`（插入）、`logout`（删除）、`clientCloseException`（删除）中持有**读锁**去修改 `unordered_map`，而这三个操作会并发发生：

- muduo 使用 **4 个 IO 线程**（`src/server/chatserver.cpp:18` — `_server.setThreadNum(4)`）
- 多个客户端同时连接/断开是常态

两个用户同时登录 → 两个线程同时持读锁 → 同并发 `insert` 同一个 `unordered_map` → **数据竞争（未定义行为）**。

实际表现：偶发崩溃、迭代器失效、map 内部结构损坏 —— 且**难以复现**，是最难排查的一类 bug。

**修改建议**

三处写操作改用独占锁：

```cpp
// src/server/chatservice.cpp:86 附近
std::unique_lock<std::shared_mutex> lock(_connMutex);   // shared_lock → unique_lock
_userConnMap.insert({id, conn});
_connUserMap.insert({conn, id});
```

`237`、`303`、`358` 三处纯查找**保持 `shared_lock` 不动** —— 那里用读锁是正确的。

### P0-3 Redis 析构漏释放订阅连接 👁

**位置**：`src/server/redis/redis.cpp:11-14`

```cpp
Redis::~Redis()
{
    if (_publish_context != nullptr)
    {
        redisFree(_publish_context);        // ✅ 正确
    }
    if (_subscribe_context != nullptr)
    {
        redisFree(_publish_context);        // ❌ 应为 _subscribe_context
    }
}
```

**问题**：典型的复制粘贴笔误 —— 第二个 `if` 判断的是 `_subscribe_context`，释放的却是 `_publish_context`。

**后果**：`_publish_context` 被 `redisFree` 两次（**双重释放**，本身就是未定义行为），而 `_subscribe_context` **从未释放**。在服务端正常退出路径上触发。

**修改建议**

```cpp
if (_subscribe_context != nullptr)
{
    redisFree(_subscribe_context);          // 改这一处
}
```

### P0-4 queryGroups 三重缺陷 👁

**位置**：`src/server/groupmodel.cpp:33-81`（函数 `GroupModel::queryGroups`）

该函数用于登录后下发"我所在的群 + 每个群的成员列表"。经现读确认，存在**三个独立缺陷**：

#### 缺陷 ①：SQL 查错了对象（`:61-63`）

```cpp
sprintf(sql, "select a.id,a.groupname,a.groupdesc from AllGroup a inner join\
    GroupUser b on b.groupid=a.id where b.groupid=%d",
        group.getId());
```

这个查询 `select` 的是 `AllGroup` 的字段，`join` 条件与 `where` 条件都在描述"群自身"，**查出来的仍然是群的信息，而不是群成员**。

要取成员列表，应 `join` 到 **`User`** 表：

```sql
SELECT a.id, a.name, b.role
FROM User a
INNER JOIN GroupUser b ON b.userid = a.id
WHERE b.groupid = %d
```

#### 缺陷 ②：字段错位（`:74`）

```cpp
user.setRole(row[2]);     // 按当前 SQL，row[2] 是 groupdesc（群描述），不是 role
```

即便 SQL 改对了，也要确保列序与 `row[]` 索引对应。

#### 缺陷 ③：循环内复用未重连的 MySQL 对象（`:41` vs `:65`）

```cpp
MySQL mysql;                       // :41  在循环外创建一次
if (mysql.connect())               // :42  只 connect 一次
{
    MYSQL_RES *res = mysql.query(sql);
    // ...
}
for (Group &group : groupVec)      // :59  进入循环
{
    MYSQL_RES *res = mysql.query(sql);   // :65  直接用，没有重新 connect()
    // ...
}
```

本项目的 DAO 惯例是**每次操作新建连接**（见 `usermodel.cpp:14-15`、`friendmodel.cpp:9-10` 等），此处打破惯例。

**后果**：登录后 `showCurrentUserData()` 打印的群成员信息**是错误的**（角色字段串成了群描述），且可能根本查不到成员。

**修改建议**：修正 SQL 到 `User` 表、修正 `row[]` 索引、在循环内为每个群单独建连接（或复用同一个连接但明确其生命周期）。

## 三、P1 级问题（安全与健壮性）

### P1-5 SQL 全量 sprintf 拼接，存在注入 👁

**位置**：六个 DAO 文件全部命中

| 文件 | 行号 | 示例 |
|---|---|---|
| `src/server/usermodel.cpp` | `:10` | `insert into User(name,password,state) values('%s','%s','%s')` |
| `src/server/usermodel.cpp` | `:30` | `select * from User where name = '%s'` |
| `src/server/usermodel.cpp` | `:56` | `select * from User where id = '%d'` |
| `src/server/friendmodel.cpp` | `:7-8` | `insert into Friend values(%d,%d)` |
| `src/server/groupmodel.cpp` | `:7` | `insert into AllGroup(groupname,groupdesc) values('%s','%s')` |
| `src/server/offlinemessgae.cpp` | `:7` | `insert into OfflineMessage values('%d','%s')` |

**风险点**

`name`、`password`、**`message`（聊天内容，用户完全可控）** 均未经转义直接拼进 SQL。攻击面：

- 注册一个用户名 `a'); drop table User; --`
- 发一条含**单引号**的聊天消息（甚至不需要恶意，正常输入"it's ok"就可能破坏语句）

**修改建议**

最小改动 —— 改用 `mysql_real_escape_string` 后再拼接：

```cpp
char esc[2048];
mysql_real_escape_string(mysql.getConnection(), esc, message.c_str(), message.size());
sprintf(sql, "insert into OfflineMessage values('%d','%s')", userid, esc);
```

更彻底 —— 改用 MySQL 预编译语句（`mysql_stmt_prepare` / `mysql_stmt_bind_param`），从根上消除拼接。

### P1-7 接收线程 exit(-1) 直接杀进程 👁

**位置**：`src/client/main.cpp:291-295`

```cpp
void readTaskHandler(int clientfd)
{
    while (true)
    {
        char buffer[1024] = {0};
        int len = recv(clientfd, buffer, 1024, 0);
        if (-1 == len || 0 == len)
        {
            close(clientfd);
            exit(-1);        // ❌ 从 detach 线程里直接终止整个进程
        }
        // ...
    }
}
```

**问题**：服务端一旦断开（重启、崩溃、网络中断），客户端**整个进程立即静默退出**：
- 用户看不到任何提示（"连接已断开"都没有）
- 不给机会重连或返回主菜单
- 该线程是 `detach` 的（`src/client/main.cpp:101`），直接 `exit` 更显粗暴

**修改建议**：设置原子标志位，由主线程检测后优雅处理：

```cpp
std::atomic<bool> g_serverDisconnected{false};   // 已有 <atomic> 头（:8）

// 接收线程内
if (-1 == len || 0 == len) { g_serverDisconnected.store(true); break; }

// 主循环内检测该标志，提示用户并决定退出或重连
```

### P1-8 无心跳机制，掉线用户状态挂死 👁

**位置**：影响 `src/server/chatservice.cpp:73-80`（重复登录拦截）

```cpp
if (user.getState() == "online")
{
    response["msgid"] = LOGIN_MSG_ACK;
    response["errno"] = 2;
    response["errmsg"] = "该账户已经登录";       // :78
    conn->send(response.dump());
}
```

**问题**：项目没有应用层心跳。客户端异常掉线（拔网线、进程被 kill、主机休眠）时，服务端**只能等 TCP 自身超时**（可能长达数十分钟）。

在此期间：
- 该用户 `state` 仍是 `online`
- **无法重新登录** —— 被 `:73-80` 拦下，提示"该账户已经登录"

**修改建议**：使用 muduo 内置的空闲检测：

```cpp
// 在 ChatServer 构造函数中
_server.setIdleCallback(...);     // 配合 setThreadNum 同一位置，chatserver.cpp:18 附近
```

同时可考虑加应用层 ping/pong（`EnMsgType` 中新增一种消息类型，`include/public.hpp:3-17`）。

### P1-9 客户端输入流处理不统一 👁 / ⚠️

**位置**：`src/client/main.cpp` 三处风格不一致

| 位置 | 场景 | 当前写法 |
|---|---|---|
| `:111` | 主菜单选号 | `cin >> choice;` + `:112-117` 失败处理 |
| `:127-130` | 登录的用户名/密码 | `cin >> name;` → `cin.get();` → `cin.getline(pwd, 50);` |
| `:165,167` | 注册的用户名/密码 | `cin>>name;` → `cin>>pwd;` |
| `:368` | 主菜单命令 | `cin.getline(buffer, 1024);` |

**问题**

1. `:111` 读完 `choice` 后**换行符残留**在输入缓冲区。
2. `:127-130` 的登录分支依赖 `:128` 那个 `cin.get()` **精确吃掉**残留换行 —— 一旦有人改动（或增删一行）这行，`:130` 的 `getline` 就会读到空串，密码为空。
3. `:165,167` 注册分支全用 `>>`，**密码含空格会被截断**。
4. 三类写法混用，维护时极易踩坑。

> **历史说明**：该处代码在 2026-09-25 16:34 被修改过（原先注册分支使用 `cin.getline`）。**上述描述对应当前版本**，修改前的相关分析已不适用。

**修改建议**：统一为一种风格。推荐全部使用 `std::getline`，需要数字时再转换：

```cpp
std::string line;
std::getline(std::cin, line);
int choice = std::stoi(line);        // 需处理异常
```

这样换行符由 `getline` 自行消费，不会残留，也支持含空格的输入。

### 6.2 P0-1 复现用例（粘包）

```python
import socket, json

def msg(mid, name):
    return (json.dumps({"msgid": mid, "name": name, "password": "123456"}) + "\x00").encode()

s = socket.socket(); s.connect(("127.0.0.1", 6000)); s.settimeout(4)
s.sendall(msg(2, "frameA") + msg(2, "frameB"))   # 两条消息合并为一次写入

got = []
try:
    while True:
        d = s.recv(4096)
        if not d: break
        got.append(d.decode(errors="replace"))
except Exception:
    pass
print("响应条数:", len(got))        # 当前实测输出: 1  （应为 2）
```
